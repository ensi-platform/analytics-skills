# Architecture Decision Record (ADR)

## Фича: Управление баннерами

**Дата:** 03.11.2026
**Версия:** 1.3
**Статус:** Согласован

**Основание:** Документ разработан на основе [BRD](01-BRD.md) (BRD v1.3).

---

## 1. Контекст

Необходимо реализовать функциональность управления баннерами на платформе Ensi. Баннеры отображаются на главной странице витрины и поддерживают три типа: главный (одиночное изображение), слайдер (несколько изображений с перелистыванием) и плитка (набор изображений сеткой). Администратор управляет баннерами через админ-панель: создание, редактирование, удаление, загрузка изображений, указание ссылок и дат активности.

Бизнес-требования (BR-01–BR-16) и ограничения зафиксированы в согласованном BRD. ADR принимает архитектурные решения до детализации FR; функциональные требования будут сформированы на основе этого ADR.

На платформе Ensi уже существует сервис **CMS**, отвечающий за управление нетоварным контентом, включая баннеры, информационные страницы и SEO. Это накладывает ожидание, что функциональность баннеров будет реализована как расширение существующего CMS-сервиса, а не как отдельный микросервис.

**Ограничения:**
- Производительность: публичный API должен отвечать ≤500 мс при 1000 баннерах
- Главная страница с баннерами должна загружаться ≤2 секунд
- Доступность сервиса: 99.5%
- Поддерживаемые форматы изображений: JPEG, PNG до 25 МБ
- Кодовая база Ensi — open-source (SOA, API-first, Headless)

---

## 2. Задействованные сервисы

| Сервис | Назначение |
|---|---|
| **CMS** | Бэкенд-сервис управления контентом. Реализует CRUD для баннеров, хранит данные в своей БД, обслуживает публичный API и админ-панель |
| **BFF** | Backend For Frontend. Проксирует запросы витрины к CMS. Отвечает за агрегацию данных и кеширование публичных эндпоинтов |
| **Admin GUI Backend** | BFF админ-панели, существующий сервис платформы. Единая точка входа для Admin UI: проксирует CRUD баннеров и загрузку изображений в CMS, проверяет аутентификацию и права администратора |
| **Admin UI** | Интерфейс админ-панели. Работает через Admin GUI Backend и не обращается к CMS напрямую |
| **Frontend** | Публичная витрина сайта. Запрашивает активные баннеры через BFF и отрисовывает их согласно типу (main, slider, grid) |
| **Object Storage** | Внешнее хранилище для файлов изображений (S3-совместимое, MinIO или аналоги). CMS загружает файлы сюда и сохраняет URL |

---

## 3. Схема взаимодействия сервисов

**Схема:** [diagrams/architecture.c4](diagrams/architecture.c4) — открывается в LikeC4 (расширение `likec4.likec4-vscode` или `npx likec4@latest start`).

**Потоки:**

- **Admin UI → Admin GUI Backend → CMS:** CRUD баннеров (`/v1/admin/banners`) и загрузка изображений (`POST /v1/admin/banners/upload`) по HTTP. Admin UI не знает внутренних адресов CMS — вызовы проксирует BFF админ-панели.
- **CMS → Object Storage:** запись и чтение файлов изображений по S3 API.
- **CMS → CMS DB:** хранение баннеров, изображений, связей и дат активности (SQL).
- **Посетитель → Frontend:** открывает главную страницу, витрина отрисовывает баннеры по типу.
- **Frontend → BFF → CMS:** чтение активных баннеров (`GET /v1/banners` → `GET /v1/internal/banners`), ответ кешируется на 60 секунд.

## 4. Принятые решения

### ADR-01: Расширение существующего сервиса CMS

**Решение:**
Реализовать функциональность баннеров как новый модуль внутри существующего сервиса **CMS**, а не как отдельный микросервис.

**Обоснование:**
- Сервис CMS уже предназначен для управления нетоварным контентом (см. карту проекта — домен Content)
- На сайте Ensi CMS уже заявлен с функцией «Создание и управление баннерами» — это логичное расширение
- Баннеры разделяют с CMS общую кодовую базу, БД, инфраструктуру и процессы деплоя
- Выделение отдельного сервиса неоправданно увеличит operational overhead (деплой, мониторинг, CI/CD) для простой CRUD-сущности

**Риски:**
- Рост связанности внутри CMS: если в будущем появится много контентных фич, CMS может стать «тяжёлым» монолитом. Митигация: модульная архитектура внутри сервиса с чёткими границами доменов (banners, pages, seo)

### ADR-02: Реляционная модель данных (SQL)

**Решение:**
Использовать реляционную БД (PostgreSQL, существующую в стеке CMS) с таблицами `banners` и `banner_image_links` со связью один-ко-многим.

**Обоснование:**
- Данные баннеров строго структурированы (поля, типы, связи)
- FR чётко определяет схему — нет необходимости в схеме-на-лету (NoSQL)
- Реляционная модель обеспечивает referential integrity, транзакционность при массовых операциях и поддерживает фильтрацию/сортировку (FR-10, FR-11)
- PostgreSQL уже используется в стеке CMS — не требуется новая инфраструктура

**Риски:**
- При росте числа баннеров выборка по диапазону дат может замедлиться. Митигация: индексы по `start_date` и `end_date`

### ADR-03: Внешнее объектное хранилище для изображений

**Решение:**
Изображения баннеров хранить во внешнем S3-совместимом объектном хранилище (MinIO / AWS S3 / Yandex Object Storage). В БД сохранять только URL изображения. Серверная валидация (MIME-тип, размер до 25 МБ) — на этапе загрузки через CMS.

**Обоснование:**
- Хранение бинарных файлов в БД (BLOB) деградирует производительность как БД, так и API (сериализация)
- CDN-доставка изображений критична для производительности главной страницы (NFR: ≤2 сек)
- S3-совместимые хранилища масштабируются независимо от БД
- Ensi-проект уже использует объектное хранилище для других файлов (товарные изображения)

**Риски:**
- Дополнительная точка отказа (storage недоступен → битые изображения). Митигация: fallback-заглушка на фронте, healthcheck

### ADR-04: BFF-прокси для публичного API баннеров

**Решение:**
Публичный эндпоинт `GET /v1/banners` (FR-01, FR-15, FR-16) реализовать через BFF-слой. BFF проксирует запрос к внутреннему API CMS. Админ-панель обращается к CMS через существующий BFF админки — Admin GUI Backend (см. раздел 2), поэтому публичный и административный трафики разделены.

**Обоснование:**
- Ensi следует принципу Headless: фронт витрины не должен иметь прямого доступа к сервисам
- BFF изолирует витрину от изменений внутренней структуры CMS
- BFF может кешировать ответ (см. ADR-05) и агрегировать данные с другими сервисами
- Админ-трафик идёт через Admin GUI Backend так же, как в остальных разделах платформы: Admin UI не знает внутренних адресов сервисов, а проверка прав выполняется на BFF

**Риски:**
- Дополнительная сетевая задержка (Frontend → BFF → CMS). Митигация: кеширование, keep-alive соединения

### ADR-05: Кеширование публичного эндпоинта (TTL 60 сек)

**Решение:**
Применить кеширование ответа `GET /v1/banners` на уровне BFF с TTL = 60 секунд. Инвалидация кеша при изменении баннеров (создание, редактирование, удаление).

**Обоснование:**
- Баннеры меняются редко (администратором, не пользователями) — высокая ratio read/write
- NFR требует время ответа ≤500 мс и загрузку главной ≤2 сек — кеш критичен
- TTL = 60 сек обеспечивает актуальность данных с задержкой не более минуты, что приемлемо для маркетингового контента

**Риски:**
- Устаревшие данные до 60 сек при срочной смене баннера. Митигация: ручная инвалидация (кнопка «Сбросить кеш» в админке)
- Кеш может быть неконсистентным при ошибках инвалидации. Митигация: fallback на прямой запрос в CMS

## 5. Альтернативы

### Вариант A: Выделенный микросервис `banners`

**Плюсы:**
- Полная изоляция кодовой базы и данных
- Независимый деплой и масштабирование

**Минусы:**
- Операционные расходы: новый репозиторий, CI/CD, мониторинг, инфраструктура БД
- Дублирование общего функционала (загрузка файлов, валидация, авторизация)
- Избыточность для простой CRUD-сущности

**Причина отклонения:**
Баннеры — часть контентного домена, который уже покрыт сервисом CMS. Выделение не приносит архитектурных выгод, но увеличивает стоимость владения.

### Вариант B: Хранение изображений в БД (base64 / BLOB)

**Плюсы:**
- Меньше движущихся частей (не требуется объектное хранилище)
- Упрощённое резервное копирование (всё в одной БД)

**Минусы:**
- Рост размера БД (изображения до 25 МБ × тысячи баннеров)
- Деградация производительности при запросах с выборкой полей
- Невозможность использовать CDN для доставки изображений

**Причина отклонения:**
Критично для производительности главной страницы — без CDN время загрузки превысит NFR (2 сек). Ensi уже использует объектное хранилище для товарных изображений.

### Вариант C: Хранение дат активности в UTC без указания таймзоны

**Плюсы:**
- Упрощённая логика фильтрации

**Минусы:**
- Администратор в другом часовом поясе увидит неожиданное время включения/отключения баннера

**Причина отклонения:**
Принято решение хранить даты в UTC, но в админ-панели отображать с учётом таймзоны сайта (см. риск в BRD).

### Вариант D: Прямой доступ Frontend → CMS (без BFF)

**Плюсы:**
- Меньше сетевых прыжков, ниже задержка

**Минусы:**
- Нарушение Headless-принципа Ensi
- Фронт витрины должен знать о внутренней структуре CMS
- Невозможность кеширования на общем слое

**Причина отклонения:**
Противоречит архитектурному принципу Headless, принятому в Ensi Platform.

## 6. Последствия

### Положительные

- Функциональность баннеров вписана в существующую архитектуру Ensi, не требует новых сервисов
- Изображения доставляются через CDN — главная страница грузится быстро
- Публичный API кеширован — нагрузка на CMS минимальна
- Админ-панель и витрина разделены (Headless) — изменения в админке не затрагивают фронт
- Реляционная модель проста, трассируема и легко поддерживается

### Отрицательные

- Дополнительная сетевая задержка через BFF (частично компенсируется кешем)
- Задержка обновления баннеров на витрине до 60 сек (TTL кеша)
- При недоступности объектного хранилища пользователи видят битые изображения

### Риски

| Риск | Митигация |
|---|---|
| Рост CMS до монолита при добавлении новых контентных фич | Модульная архитектура, выделение bounded context внутри сервиса |
| Устаревшие баннеры в кеше при срочных изменениях | Кнопка ручной инвалидации кеша в админ-панели |
| Недоступность S3-хранилища → отсутствие изображений | Fallback-заглушка на фронте, healthcheck хранилища |
| Конфликт нескольких активных главных баннеров | Ограничение: только один активный main-баннер на главной (FR-18; валидация в CMS) |
