## 1. Общие условия и тестовые данные

### Выполнение и блокировки

Кейсы спроектированы, но не выполнялись: результатов Pass/Fail и измерений реализации нет. **ENV-01** запрещает выполнение всех кейсов до предоставления реализации, стенда, доступа, разрешённых фикстур, наблюдаемости и средств управляемого воспроизведения сбоев. Это общий блокер выполнения, а не утверждение, что все требования не определены.

Отдельная пометка «Заблокирован по уточнению Q-…» означает, что для конкретной проверки не хватает точного сопоставления или параметра из уже открытых вопросов FR. Кейсы без такой пометки имеют определённые ожидаемые результаты, но также не выполняются до снятия ENV-01. Согласование документа не снимает эти блокировки автоматически.

### Фикстура D0

1. На изолированных разрешённых данных подготовить S_A с P_A, S_B с P_B, а также S_N без контакта. T_A и T_A2 связаны с единственным S_A, T_B — с единственным S_B, T_N — с S_N. Все обозначения заменяются фактическими положительными integer-id из фикстур; id из примеров FR не предполагаются существующими. Для T_MISSING заранее подтвердить отсутствие выбранного положительного id.
2. Форматные входные данные: **P_A = +70000000000**, отображение `+7 (000) 000-00-00`; **P_B = +70000000001**, отображение `+7 (000) 000-00-01`. Это синтетические входы для согласованной проверки «только маска», не реальные контакты и не подтверждение национальной принадлежности/действительности номера. Реальные звонки по ним не выполняются.
3. Для системного сценария звонка **P_CALL** — разрешённый владельцем стенда тестовый российский номер; значение требует предоставления. Проверка останавливается до фактического телефонного вызова; номера и учётные данные QA не выдумывает.
4. **G** — чистая гостевая сессия; **B** — покупатель с фактической сессией; **M** — контент-менеджер с подтверждённым правом изменения нужного продавца; **R** — контрольная роль без этого права. Реальные учётные данные/идентификаторы разрешений предоставляет среда. Точные сопоставления для специальных проверок — Q-01.
5. **AVAIL(id)** — GET `/v1/products/{product_id}/seller-phone-availability`; **PHONE(id)** — GET `/v1/products/{product_id}/seller-phone`, где в path подставляется фактический id. Запросы по умолчанию: `Accept: application/json`, без `Authorization`, без тела и дополнительных query-параметров. Административные действия выполняются по фактическому контракту инсталляции; несуществующие административные endpoints и коды не назначаются.
6. Сбои, удержание ответов, порядок доставки и наблюдение запросов воспроизводятся разрешёнными средствами тестовой среды. Подмена ответа для проверки клиентского обработчика не доказывает соответствие реального сервера контракту; интеграционные/API-кейсы проверяют сервер отдельно.
7. Для нагрузки используются ровно 50 независимых клиентов с подготовленным скрытым номером и по одним нажатием по общему управляемому сигналу. Для каждого отдельно фиксируются фактические t_click и t_visible. Порог — не более 3 секунд каждому; точность наблюдения должна позволять сравнение с ним. Нормы RPS, длительность пика, суточная аудитория и автоматическая ошибка на третьей секунде не добавляются.
8. Перед каждым независимым прогоном восстановить исходные связи, контакт и права. После него снять перехваты/сбои, восстановить изменённые контакты и удалить только специально созданные фикстуры по правилам среды. Изменения общих данных не переносятся между независимыми прогонами, кроме явно заданной последовательности внутри кейса.
