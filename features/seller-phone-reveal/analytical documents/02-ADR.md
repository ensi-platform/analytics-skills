# Architecture Decision Record (ADR)

## Фича: Раскрытие телефона продавца в карточке товара

**Дата:** 11.11.2026
**Версия:** 1.0
**Статус:** Согласован

**Основание:** документ разработан на основе согласованного [BRD](01-BRD.md) (BRD v1.0, согласован пользователем 11.11.2026) и [карты проекта](../../../PROJECT-MAP.md) v1.1.

## 1. Контекст

У товара один продавец. Покупатель, включая гостя, раскрывает его общий номер в текущей карточке без перезагрузки и может начать звонок с телефона. Номер ведёт контент-менеджер в админке через Inputmask; добавочных номеров и дополнительной валидации нет. При отсутствии номера кнопка скрыта, при ошибке показывается установленное в BRD сообщение и доступно повторное нажатие.

При одновременном нажатии 50 пользователями номер должен отобразиться каждому не позднее 3 секунд от его нажатия. Поддерживаются последние три версии указанных в BRD браузеров и мобильных систем. Срок реализации — 2 недели после согласования документов. Дополнительный профиль нагрузки не требуется для принятия архитектуры.

Это целевая архитектура доработки. Карта проекта описывает ответственность сервисов, но не подтверждает наличие конкретных полей, операций и связей в установленной версии Ensi. Исходников сайта и сервисов в этом репозитории нет. Решения ниже предложены аналитиком и ожидают согласования; вопросы к фактической реализации перечислены в разделе 6.

## 2. Задействованные сервисы

| Сервис или компонент | Назначение в целевой архитектуре | Основание |
|---|---|---|
| Витрина сайта | Кнопка, асинхронное раскрытие, сообщение об ошибке и переход к вызову на устройстве. | Сайт и карточка товара из BRD. |
| Публичная серверная граница сайта | Получение признака наличия номера и выдача номера по действию покупателя; разрешение связи товара с продавцом и обращение к внутренним сервисам. | Логическая часть существующего сайта, а не предложение нового самостоятельного сервиса. Фактическое размещение требует проверки. |
| Offers | Получение связи товарного предложения с единственным продавцом в целевой схеме. | Домен торговых предложений из карты проекта; доступный контракт связи с продавцом требует проверки. |
| Business Units | Владелец общего контакта продавца; чтение наличия/номера и сохранение изменений через собственные операции. | Владелец продавцов по карте проекта, раздел 3.4. |
| Хранилище Business Units | Сохранение контакта в существующем хранилище сервиса. | Ответственность Business Units; конкретная СУБД и структура требуют проверки. |
| Admin UI | Ввод и изменение номера контент-менеджером с Inputmask. | Админка из BRD. |
| Admin GUI Backend | Серверная граница админки: проверка доступа и обращение к Business Units. | Карта проекта, раздел 3.6. |
| Admin Auth | Проверка административной сессии и полномочий контент-менеджера в составе существующей модели доступа. | Карта проекта, раздел 3.4. |

Приложение звонка — средство устройства покупателя, не сервис Ensi. Для этой фичи не вводятся отдельный сервис телефонов, новая база данных, брокер или интеграция с оператором телефонии.

## 3. Схема взаимодействия сервисов

**Схема:** [diagrams/architecture.c4](diagrams/architecture.c4).

**Конфигурация:** [diagrams/likec4.config.json](diagrams/likec4.config.json), отдельный проект `seller-phone-reveal`.

В одном файле находятся общая схема, публичный поток, административный поток и динамический вид раскрытия номера. Публичная граница показана как логический серверный компонент существующего сайта: её название не утверждает наличие нового развёртываемого сервиса.

**Потоки:**

- Покупатель → витрина → публичная граница сайта: HTTPS; при подготовке карточки передаётся признак наличия контакта, а по нажатию отдельно запрашивается номер.
- Публичная граница → Offers → публичная граница: внутренний HTTP/REST для разрешения единственного продавца товара; произвольная связь товара и продавца из браузера не принимается на доверии.
- Публичная граница → Business Units → собственное хранилище: внутренний HTTP/REST и доступ сервиса к своему хранилищу; для карточки возвращается наличие контакта, для раскрытия — текущий номер.
- Контент-менеджер → Admin UI → Admin GUI Backend → Admin Auth и Business Units: HTTPS и внутренний HTTP/REST; изменение контакта проходит через административную проверку доступа.
- Business Units → своё хранилище: сохранение общего контакта продавца; остальные компоненты не обращаются к этому хранилищу напрямую.
- Витрина → системное приложение звонка: телефонная ссылка на устройстве покупателя после раскрытия номера; вызов не проходит через сервисы платформы.

## 4. Принятые решения

Решения ADR v1.0 согласованы пользователем 11.11.2026 сообщением «согласую документ» в ответ на уточнение о согласовании ADR v1.0 фичи «Раскрытие телефона продавца».

### ADR-01: Единственный владелец контакта — Business Units

**Решение:** хранить общий контакт в существующем домене продавцов Business Units. Чтение и изменение выполнять через операции этого сервиса, доработав их при необходимости. Не копировать контакт в каждый товар и не предоставлять другим сервисам прямой доступ к его базе.

**Обоснование:** BR-06–07; продавцами по карте проекта управляет Business Units. Один источник контакта соответствует общему номеру продавца и ограничивает объём доработки двухнедельным сроком.

**Риски:** существующий контакт и его назначение не проверены. Нельзя автоматически переиспользовать любой найденный телефон продавца: перед реализацией требуется подтвердить, что это именно контакт для покупателей, а не внутренний реквизит.

### ADR-02: Отдельное синхронное чтение по действию покупателя

**Решение:** витрина получает номер асинхронным запросом к публичной серверной границе сайта после нажатия кнопки. В начальные данные карточки включается только признак наличия контакта. Полный номер не помещается заранее в разметку, скрытые элементы или данные карточки, переданные браузеру.

Серверная граница разрешает единственного продавца по товарному контексту через Offers и читает контакт в Business Units. Доступ к раскрытию не требует покупательской сессии. Внутренние административные операции Business Units не становятся публичными.

**Обоснование:** BR-01–04, BR-06, BR-08; разделение наличия и номера позволяет скрывать кнопку при отсутствии контакта и раскрывать данные по действию пользователя. Это архитектурный выбор способа раскрытия, а не дополнительное условие авторизации.

**Риски:** контракт связи товара и продавца и публичная точка входа требуют проверки. Доступность номера всем гостям означает, что скрытие до нажатия не является защитой от программного получения через публичный сценарий.

### ADR-03: Изменение контакта через существующую административную границу

**Решение:** контент-менеджер работает в Admin UI; запрос изменения проходит через Admin GUI Backend с использованием Admin Auth и далее в Business Units. Административная проверка права на изменение выполняется на сервере и не заменяется скрытием элемента интерфейса.

**Обоснование:** BR-07 и существующий маршрут админ-панели из карты проекта. Решение сохраняет разделение публичного чтения и административного изменения общего контакта.

**Риски:** действующие разрешения и операции управления продавцом не подтверждены. Их соответствие роли контент-менеджера проверяется при детализации FR; новые полномочия других ролей этим ADR не вводятся.

### ADR-04: Inputmask для ввода, телефонная ссылка для начала звонка

**Решение:** использовать выбранную пользователем Inputmask в существующей админке для российского формата без добавочного номера. Дополнительную бизнес-валидацию номера, проверку владельца и подтверждение кодом не добавлять. Маска ограничивает ввод, но не доказывает актуальность контакта.

На витрине номер отображается как текст и телефонная ссылка `tel:` с представлением того же номера для устройства. Подготовка значения ссылки и безопасный вывод текста не должны вводить дополнительные проверки допустимости телефонных номеров. Конкретная маска и правила представления будут описаны в FR.

**Обоснование:** BR-05, BR-10–11 и прямое решение пользователя об Inputmask и отсутствии дополнительной валидации. Начало звонка обеспечивается устройством покупателя, без собственной телефонии платформы.

**Риски:** необходима проверка интеграции выбранной версии Inputmask с фактическим стеком админки и поддержки сценария в установленной матрице браузеров и устройств. Ошибочный, но соответствующий маске контакт остаётся возможным.

### ADR-05: Короткий путь чтения без дополнительной инфраструктуры

**Решение:** раскрытие выполняется синхронной серверной цепочкой разрешения продавца и чтения контакта. Очередь фоновых заданий и опрос результата не применяются. На старте доработки не вводить распределённый кеш и отдельную копию контактов; читать источник Business Units. Полные ответы с номером исключить из общего кеширования публичных страниц.

Настройки соединений, конкурентности и внутренних таймаутов подобрать так, чтобы общая цепочка вместе с сетью и отображением укладывалась в 3 секунды при одновременном нажатии 50 пользователями. Новая числовая норма запросов в секунду или длительности нагрузки не устанавливается.

**Обоснование:** раздел 8 BRD и двухнедельный срок. Прямое чтение ограничивает число компонентов и не требует механизма синхронизации копий контакта.

**Риски:** достаточность ресурсов и фактическое время зависимых сервисов ещё не измерены. Соответствие пределу 3 секунд подтверждается только проверкой будущей реализации, а не данным решением. Трёхсекундный предел не превращается автоматически в отдельное бизнес-правило о времени показа ошибки.

### ADR-06: Изолированное состояние попытки и ручной повтор

**Решение:** в витрине выделить состояние текущей попытки раскрытия. Ошибка завершает эту попытку, показывает сообщение из BRD и возвращает возможность повторного нажатия. Поздний ответ от прежней попытки или другой карточки не должен подменять результат текущего товара. Повторное нажатие после ошибки запускает новое чтение, не требуя перезагрузки страницы.

Для диагностики использовать существующие журналы и измерение длительности вызовов без записи самого номера. Отдельную бизнес-аналитику раскрытий и статистику звонков не вводить.

**Обоснование:** BR-03–04, BR-06, BR-09, BR-12 и требование времени раскрытия. Разделение попыток позволяет безопасно восстановить сценарий после ошибки.

**Риски:** состояния отсутствующего контакта и технической ошибки необходимо различать в будущем публичном контракте. Конкретные ответы и тексты, кроме уже установленного сообщения об ошибке, детализируются в FR по BRD.

## 5. Альтернативы

### Вариант A: Передавать полный номер вместе с карточкой и скрывать его на клиенте

**Плюсы:** после загрузки карточки раскрытие не требует отдельного сетевого обращения.

**Минусы:** полный номер передаётся до действия покупателя, попадает в данные карточки и потенциально в её кеши; обновление контакта зависит от обновления карточки.

**Причина отклонения:** выбран отдельный запрос, чтобы отделить признак наличия от выдачи номера и читать контакт в источнике. BRD требует скрытия от отображения; отказ от этой альтернативы является архитектурным предложением, а не утверждением, что она запрещена исходным запросом.

### Вариант B: Хранить копию номера в каждом товаре или отдельном сервисе контактов

**Плюсы:** копия в товаре сокращает путь чтения; отдельный сервис позволяет независимо развивать контакты.

**Минусы:** дублирование контакта требует синхронизации; отдельный сервис добавляет развёртывание и сопровождение для единственного общего реквизита продавца.

**Причина отклонения:** Business Units уже отвечает за продавцов; отдельный источник контакта или копии не обоснованы текущим объёмом и сроком реализации.

### Вариант C: Читать и изменять контакт из браузера напрямую через внутренний API Business Units

**Плюсы:** меньше промежуточных компонентов на пути запроса.

**Минусы:** связывает клиентский код с внутренними операциями сервиса; для админки обходит предусмотренный картой проекта Admin GUI Backend.

**Причина отклонения:** выбраны публичная и административная серверные границы с разными правами чтения и изменения.

## 6. Последствия

### Положительные

- Общий контакт имеет одного владельца и не размножается по товарам.
- Раскрытие доступно гостю, происходит без перезагрузки и поддерживает ручную повторную попытку.
- Используются существующие домены платформы и административная модель доступа.

### Отрицательные

- Раскрытие зависит от доступности публичной границы, Offers и Business Units.
- Возможна доработка получения признака наличия контакта и связи товара с продавцом.
- Отсутствие дополнительной валидации оставляет риск неверного контактного номера.

### Риски и необходимые проверки реализации

| ID | Риск / открытый технический вопрос | Необходимое действие |
|---|---|---|
| ARCH-Q-01 | Фактический серверный компонент публичной границы сайта и его стек не установлены. | Перед реализацией определить существующую точку входа, в которую встраивается чтение контакта; не создавать новый сервис по одному названию на схеме. |
| ARCH-Q-02 | Контракты Offers и Business Units, существующий контакт продавца, его назначение и административные разрешения не проверены. | Проверить исходники и контракты целевой инсталляции; в FR зафиксировать необходимые доработки и фактическую связь товара с единственным продавцом. |
| ARCH-Q-03 | Нет измерений времени раскрытия и проверки совместимости на реализации. | Проверить 50 одновременных нажатий с пределом 3 секунды для каждого и матрицу последних трёх версий из BRD. Это проверка заданного сценария, а не запрос дополнительных нагрузочных требований. |

Эти вопросы относятся к фактической инсталляции и подготовке реализации, а не к повторному согласованию уже установленных бизнес-правил. Изменение ответственности сервисов при обнаружении противоречий оформляется новой версией ADR по общим правилам.

**Проверка схемы:** 11.11.2026 выполнен `validate .` из папки `diagrams/` с LikeC4 1.60.0. Команда завершилась с кодом 0 и результатом `✓ Valid (1 files)`: проверен один исходный файл отдельного проекта `seller-phone-reveal`, содержащий четыре вида. Это проверка синтаксиса схемы; время раскрытия номера и совместимость проверяются на будущей реализации.
