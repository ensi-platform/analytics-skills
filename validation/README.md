# Валидация документов фичи

Валидация — обязательный шаг перед показом документа пользователю. Она проверяет не бизнес-истинность требований, а готовность документа: основания, структуру, версии, идентификаторы, трассировку и отсутствие выдуманных данных.

## Когда выполняется

- для новых фич;
- перед показом BRD, ADR и FR;
- перед показом QA-комплекта;
- после согласования всех документов — финальная проверка фичи.

Существующие фичи не перерабатываются только ради валидации.

## Кто выполняет

1. **Автор** (`analyst` или `qa`) — самопроверка по чек-листу.
2. **Основной агент** — проверка тех же пунктов по файлам и заполнение отчёта.
3. **Пользователь** — читает резюме и вердикт, принимает бизнес-решения и согласует документы.

Отдельный агент-валидатор и скрипты в v1 не используются.

## Отчёт

Отчёт ведётся в `features/<slug>/validation/Validation.md`:

- шаблон — `validation/template.md`;
- заполненный пример — `validation/example.md`.

В отчёте фиксируются:

- проверенные документы и версии;
- результат по каждому пункту с доказательством;
- находки и их статус;
- согласованные версии;
- история прогонов;
- итог фичи после финальной проверки.

Отчёт не согласуется пользователем отдельно: он фиксирует результат проверки документов. Пользователь согласует сами BRD, ADR, FR и QA-документы.

## Чек-лист

| № | Проверка | Уровень |
|---|---|---|
| 1 | Основания существуют, согласованы, не устарели; версии в ссылках совпадают с шапками | Блокер |
| 2 | Шапка заполнена; история есть; последняя запись соответствует версии; нет разных записей с одной версией | Блокер |
| 3 | Нет `<!-- -->`, `<...>`, `TODO`; «требует уточнения» только рядом с вопросом | Блокер |
| 4 | ID уникальны, формат соблюдён, при новой версии не потеряны | Блокер |
| 5 | Каждое BR из BRD есть в трассировке FR; нет ссылок на несуществующие FR | Блокер |
| 6 | Каждое решение ADR отражено в FR или явно отложено с причиной | Существенное |
| 7 | В Matrix есть все FR и ADR; все ID проверок существуют; нет осиротевших проверок | Блокер |
| 8 | Сводки по категориям и приоритетам сходятся; тип TC/CL един; Integration/API обоснованы | Блокер |
| 9 | Ссылки открываются; LikeC4 проходит `npx likec4 validate .`; JSON/PlantUML не сломаны | Блокер |
| 10 | Нет выдуманных HTTP-кодов, полей, ролей, сервисов, порогов; нет утверждений о выполнении без результата | Существенное |

Для BRD пункты 1, 5–8 обычно не применимы; для ADR — 5–8. Пункт 9 применим, когда в фиче есть схема или исполняемые примеры; иначе фиксируется `—`. Неприменимость фиксируется как `—` с кратким объяснением, а не как ошибка.

## Вердикты

| Вердикт | Значение |
|---|---|
| **PASS** | Все применимые пункты пройдены, открытых находок нет |
| **PASS WITH REMARKS** | Блокеров нет, но есть существенные замечания; пользователь видит их и решает |
| **FAIL** | Есть хотя бы один блокер; документ возвращается автору и не показывается как готовый |

## Правила заполнения

- По каждому пункту указывай доказательство: `файл:строка`, цитату или результат команды. Галочка без доказательства не считается.
- `требует уточнения` — допустимое обозначение неизвестного, если рядом есть вопрос. Это не заглушка.
- Находки не удаляются: исправленная помечается «Исправлено», принятая — «Принято пользователем» с датой.
- После согласования версия и дата записываются в раздел «Согласованные версии».
- Любая правка согласованного документа требует новой версии, записи в истории и повторной валидации.
- Финальная проверка выполняется после согласования всех документов: все версии и ссылки совпадают, устаревших документов нет, Matrix соответствует фактическим проверкам.

## Ограничения v1

- Количество проверок и Matrix считается вручную.
- Нет автоматической проверки хешей и «тихих» правок; согласованные версии фиксируются в отчёте.
- Ссылки и схемы проверяются вручную и командой LikeC4.

Если ручная проверка станет слишком долгой или появятся повторяющиеся ошибки, можно добавить отдельного валидатора, а затем мини-скрипт на версии, Matrix и хеши. Это не входит в v1.
