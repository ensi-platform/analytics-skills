# Скилл: Генерация ADR

## Когда применять

BRD согласован пользователем (получено подтверждение "согласовано", "ок", "дальше", "approved"). ADR создаётся до FR: сначала фиксируются архитектурные решения, затем на их основе детализируются функциональные требования.

## Входные данные

- `features/<slug>/analytical documents/01-BRD.md` — согласованный Business Requirements Document
- `PROJECT-MAP.md` — карта проекта: домены, сервисы, архитектурные принципы
- Контекст текущей архитектуры проекта (если есть другие ADR или структура)
- `templates/ADR.md` — шаблон Architecture Decision Record (путь относительно каталога скилла)

## Действия

1. **Прочитай** `01-BRD.md` из `features/<slug>/analytical documents/`. Все относительные пути `diagrams/` ниже отсчитываются от этой папки.
2. **Прочитай** `PROJECT-MAP.md` в корне проекта.
3. **Прочитай шаблон** `templates/ADR.md` (путь относительно каталога скилла).
4. **Прочитай правила** `AGENTS.md` (в корне проекта).
5. **Прочитай существующие ADR** в проекте (если есть) для понимания архитектурного контекста.
6. **Заполни шаблон**:

### Контекст
Почему возникла необходимость в архитектурном решении. Опиши бизнес-контекст, требования и ограничения из BRD, а также технические предпосылки.

### Задействованные сервисы
Список сервисов/компонентов из `PROJECT-MAP.md`, которые участвуют в реализации фичи, с описанием назначения каждого. Не выдумывай сервисы, которых нет в карте проекта.

### Схема взаимодействия
Схема — **отдельный файл** `features/<slug>/analytical documents/diagrams/architecture.c4`, а не блок кода в документе. Встроенное превью Markdown код LikeC4 не рендерит, поэтому в ADR остаются ссылка на файл и расшифровка потоков текстом.

**Создавай файл из каркаса** `templates/architecture.c4.tpl`: скопируй в `diagrams/architecture.c4` и замени пример в `model` на сервисы фичи. В каркасе уже заданы восемь видов элементов:

| kind | Форма | Цвет | Когда использовать |
|---|---|---|---|
| `actor` | `person` | indigo | пользователь, роль, действующее лицо |
| `webapp` | `browser` | primary | витрина, админ-панель, любой веб-интерфейс |
| `mobileapp` | `mobile` | primary | мобильное приложение |
| `service` | `component` | primary | сервис, контейнер, BFF, API |
| `database` | `cylinder` | green | реляционная или документная БД |
| `broker` | `queue` | amber | брокер сообщений, очередь, шина событий |
| `filestore` | `bucket` | secondary | объектное или файловое хранилище |
| `external` | `rectangle` | muted | внешняя система, чужой сервис, шлюз |

Для админ-панели используй существующий BFF платформы — **Admin GUI Backend** (см. `PROJECT-MAP.md`, раздел 3.6). Admin UI не обращается к сервисам напрямую: маршрут идёт `Admin UI → Admin GUI Backend → сервис`. Паттерн показан в каркасе.

**Правила стилизации:**
- Стили задаются **только в `specification` по виду элемента**. В `model` и `views` стили не дублируются — иначе одна и та же сущность в разных видах выглядит по-разному.
- `notation` у каждого вида обязателен: это легенда схемы. Без неё читатель не понимает, чем `cylinder` отличается от `bucket`.
- **Иконки не используем.** Ни `icon`, ни `iconSize`, ни `iconPosition` — даже если элемент кажется «пустым». Смысл несут форма, цвет и подпись.
- У каждого элемента заполняй `technology` (`PostgreSQL`, `Kafka`, `Next.js`). Иконок нет, поэтому стек виден только текстом.
- Не вводи свои формы и цвета сверх каркаса: восемь ролей покрывают архитектурные схемы, остальное — вкусовщина.

`notation` в LikeC4 помечен как экспериментальная возможность — синтаксис может измениться в мажорной версии. Если он сломается, легенду дублируй списком в разделе 3 ADR, а формы и цвета не трогай.

**Синтаксис, на котором легко споткнуться:**
- Заголовок вида задаётся свойством `title` внутри блока: `view index 'Общая схема' {` не компилируется.
- `autoLayout` без направления не проходит: либо не указывай вовсе, либо `autoLayout TopBottom`.
- Имя элемента — латиница, цифры, `-`, `_`, не начинается с цифры и не содержит `.`.

Перед сохранением проверь файл:

```sh
npx likec4@latest validate .
```

**Обязательно создай `diagrams/likec4.config.json`** рядом со схемой:

```json
{
  "$schema": "https://likec4.dev/schemas/config.json",
  "name": "<slug-фичи>"
}
```

Без него LikeC4 считает весь репозиторий одним проектом: он рекурсивно собирает все `*.c4`, и схемы разных фич падают с `Duplicate element kind` и `Duplicate view 'index'`. Файл конфига делает папку `diagrams/` отдельным проектом, и родительский проект её больше не видит. `name` должен быть уникальным в репозитории — используй slug фичи.

Все views (контекст, контейнеры, динамика) держи в одном файле. Используй только сервисы из `PROJECT-MAP.md`.

### Принятые решения
Каждое решение с ID (ADR-01, ADR-02...):
- Решение
- Обоснование (почему выбрано, на какое BR или ограничение опирается)
- Риски, если есть

### Альтернативы
Какие варианты рассматривались, почему отклонены.

### Последствия
- Положительные: что улучшится
- Отрицательные: какие компромиссы
- Риски: что может пойти не так

### Версии и история
Заполни `Дата`, `Версия`, `Статус`. В основании укажи версию BRD: `(BRD v1.0)`. Если это не первая версия — добавь строку в «Историю изменений» и объясни, что изменилось в BRD.

7. **Сохрани схему** как `features/<slug>/analytical documents/diagrams/architecture.c4`, а документ — как `features/<slug>/analytical documents/02-ADR.md`.
8. **Выведи пользователю резюме** (до 10 строк): количество принятых решений, ключевые сервисы, основные риски.
9. **Запроси подтверждение**.

## Чек-лист качества

- [ ] Каждое решение обосновано (не "выбрали PostgreSQL, потому что" — нужно конкретное обоснование)
- [ ] Решение опирается на BRD или ограничения проекта, а не на догадки
- [ ] Рассмотрено минимум 2 альтернативы
- [ ] Последствия описаны сбалансированно
- [ ] Схема взаимодействия читаема и использует сервисы из `PROJECT-MAP.md`
- [ ] Схема вынесена в `diagrams/architecture.c4`, в ADR — ссылка и расшифровка потоков текстом
- [ ] Все стили заданы в `specification` по виду элемента, в `model` и `views` их нет
- [ ] У каждого вида есть `notation` (легенда), у каждого сервиса заполнен `technology`
- [ ] Иконок нет: ни `icon`, ни `iconSize`, ни `iconPosition`
- [ ] Рядом со схемой создан `diagrams/likec4.config.json` с уникальным `name` (slug фичи), иначе схемы разных фич конфликтуют
- [ ] Синтаксис `.c4` валиден для LikeC4, файл проходит `npx likec4@latest validate .` без ошибок
- [ ] Каждое решение сформулировано проверяемым образом — его можно покрыть тест-кейсом
- [ ] ADR не описывает API-контракты и поля БД — это зона FR
- [ ] В основании указана версия BRD; раздел «История изменений» заполнен

## Чего НЕ делать

- Не переходить к FR без подтверждения пользователя
- Не придумывать бизнес-требования, которых нет в BRD
- Не подменять архитектурное решение функциональным требованием
- Не вставлять код LikeC4 в документ ADR — только ссылку на `diagrams/architecture.c4`
- Не добавлять иконки (`icon`, `iconSize`, `iconPosition`) — схема держится на формах, цветах и легенде
- Не придумывать формы и цвета сверх каркаса `templates/architecture.c4.tpl`
