# Скилл: Генерация BRD

## Когда применять

На вход пришёл запрос вида "хочу X", "нужно Y", "сделать Z". Папки фичи ещё не существует.

## Входные данные

- 1–3 строки требований от пользователя
- `PROJECT-MAP.md` — карта проекта: домены, сервисы, архитектурные принципы
- Контекст проекта (текущая структура, если есть)

## Действия

1. **Прочитай** `PROJECT-MAP.md` — чтобы не изобретать сущности и домены, которые уже существуют в проекте.
2. **Определи slug фичи** — латиница, kebab-case, без дат.
3. **Создай директорию** `features/<slug>/analytical documents/`.
4. **Прочитай шаблон** `templates/BRD.md` (путь относительно каталога скилла).
5. **Прочитай правила** `AGENTS.md` (в корне проекта).
6. **Заполни шаблон**:
   - Контекст и цель — на основе запроса пользователя
   - Проблема — какую проблему решает фича
   - Бизнес-требования — в формате BR-01, BR-02, ...
   - User Story — таблица (пользователь, действие, ожидаемый результат)
   - Ограничения — нефункциональные рамки: производительность, доступность, форматы файлов, сроки (если известны). Это вход для ADR: без ограничений архитектурные решения принимаются вслепую
   - Открытые вопросы — если данных недостаточно
   - Шапку документа — `Дата`, `Версия: 1.0`, `Статус: Черновик`
7. **Сохрани** результат как `features/<slug>/analytical documents/01-BRD.md`.
8. **Выведи пользователю краткое резюме** (до 10 строк):
   - Название фичи
   - Slug
   - Количество бизнес-требований и их перечень
   - Ключевые ограничения
   - Ключевые риски
   - Ссылку на файл
9. **Запроси подтверждение**: "BRD сформирован. Согласовано? (ок/дальше/approved)"

## Чек-лист качества

- [ ] Цель сформулирована измеримо (есть числовые или качественные критерии)
- [ ] Определены критерии успеха (KPI / success metrics)
- [ ] Описаны риски
- [ ] Нет системных деталей (API и БД — это FR, архитектура — это ADR)
- [ ] Зафиксированы известные нефункциональные ограничения (производительность, доступность, форматы файлов)
- [ ] Ограничений достаточно, чтобы на них можно было опереться в ADR
- [ ] Раздел «История изменений» заполнен
- [ ] Каждое требование имеет уникальный ID (BR-01, BR-02, ...)

## Чего НЕ делать

- Не описывать API, БД, схемы данных, диаграммы последовательности
- Не использовать техническую терминологию реализации
- Не придумывать требования, которых нет во входных данных
- Не переходить к ADR без подтверждения пользователя
