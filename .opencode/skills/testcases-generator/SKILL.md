# Скилл: Генерация тест-кейсов

## Когда применять

FR согласован пользователем (получено подтверждение). Тест-кейсы создаются последними: они проверяют и функциональные требования, и архитектурные решения.

## Входные данные

- `features/<slug>/03-FR.md` — согласованный Functional Requirements Document
- `features/<slug>/02-ADR.md` — согласованный Architecture Decision Record
- `templates/TEST-CASES.md` — шаблон тест-кейсов (путь относительно каталога скилла)

## Действия

1. **Прочитай** `03-FR.md` и `02-ADR.md` из папки фичи.
2. **Прочитай шаблон** `templates/TEST-CASES.md` (путь относительно каталога скилла).
3. **Прочитай правила** `AGENTS.md` (в корне проекта).
4. **Заполни шаблон**:

### Матрица покрытия
Две таблицы:
- FR-ID → Test ID: какие тесты покрывают какие функциональные требования.
- ADR-ID → Test ID: какие тесты проверяют какие архитектурные решения.

### Позитивные кейсы
Сценарии, при которых всё работает штатно.

### Негативные кейсы
Сценарии с некорректными данными, ошибками, отказами.

### Граничные кейсы
Граничные значения полей (пустые строки, нули, максимумы, минимумы).

### Интеграционные кейсы
Сквозные сценарии двух видов:
- **API**: последовательность вызовов и корректность контрактов.
- **E2E**: полный пользовательский путь через несколько компонентов (админка → API → хранилище → фронт).

Не требуется отдельный интеграционный тест на каждый эндпоинт. Интеграционные кейсы должны покрывать ключевые сквозные потоки и решения ADR (хранилище, кеш, интеграции).

### Формат каждого кейса

| Поле | Значение |
|---|---|
| **ID** | TC-POS-01 / TC-NEG-01 / TC-BND-01 / TC-INT-01 |
| **Название** | Краткое описание сценария |
| **Предусловия** | Что должно быть выполнено до начала теста |
| **Шаги** | Нумерованный список действий |
| **Ожидаемый результат** | Что должно произойти |
| **Ссылка на FR** | FR-ID, к которому относится кейс |

### Версии и история
Заполни `Дата`, `Версия`, `Статус`. В основании укажи версии FR и ADR: `(FR v1.0, ADR v1.0)`. Если это не первая версия — добавь строку в «Историю изменений» и объясни, что изменилось в FR или ADR.

5. **Построй сводку по приоритетам** (Critical / High / Medium / Low). Сумма по приоритетам должна совпадать с общим числом кейсов.
6. **Сохрани** как `features/<slug>/04-TEST-CASES.md`.
7. **Выведи пользователю резюме** (до 10 строк): общее количество кейсов, распределение по категориям и приоритетам, покрытие FR и ADR.
8. **Запроси подтверждение**.

## Чек-лист качества

- [ ] Каждый FR покрыт хотя бы одним тест-кейсом
- [ ] Каждое решение ADR покрыто хотя бы одним тест-кейсом
- [ ] Матрицы FR → TC и ADR → TC заполнены и не содержат ссылок на несуществующие ID
- [ ] Все кейсы учтены в сводке по приоритетам ровно один раз
- [ ] Для каждого поля формы есть негативный сценарий (невалидные данные)
- [ ] Кейсы воспроизводимы (шаги конкретны)
- [ ] Нет дублирующихся кейсов
- [ ] Интеграционные кейсы проверяют ключевые сквозные потоки, а не механически каждый эндпоинт
- [ ] В основании указаны версии FR и ADR; раздел «История изменений» заполнен

## Чего НЕ делать

- Не придумывать новые требования и архитектурные решения — только проверять существующие
- Не оставлять FR или ADR без покрытия
