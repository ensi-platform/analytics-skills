# Скилл: Генерация FR

## Когда применять

ADR согласован пользователем (получено подтверждение "согласовано", "ок", "дальше", "approved", "хорошо"). FR создаётся после ADR: архитектурные решения уже зафиксированы, остаётся описать функциональность.

## Входные данные

- `features/<slug>/01-BRD.md` — согласованный Business Requirements Document
- `features/<slug>/02-ADR.md` — согласованный Architecture Decision Record
- `PROJECT-MAP.md` — карта проекта: домены, сервисы, архитектурные принципы
- `templates/FR.md` — шаблон функциональных требований (путь относительно каталога скилла)

## Действия

1. **Прочитай** `01-BRD.md` и `02-ADR.md` из папки фичи.
2. **Прочитай** `PROJECT-MAP.md` в корне проекта.
3. **Прочитай шаблон** `templates/FR.md` (путь относительно каталога скилла).
4. **Прочитай правила** `AGENTS.md` (в корне проекта).
5. **Заполни шаблон**, покрывая все разделы:

### Функциональные требования
Формат User Story от трёх лиц:
- **Пользователь сайта** — "Как пользователь, я хочу..."
- **Администратор в панели управления** — "Как администратор, я хочу..."
- **Backend-сервис** — "Как система, я должна..."

Каждая User Story содержит: ID (FR-01...), роль, действие, обоснование, критерий приёмки.

### Модель данных
Таблицы с колонками:

| Наименование | Тип | Nullable | Описание |
|---|---|---|---|
| `id` | int | Нет | Первичный ключ |

Связи между сущностями описать текстом.

### API-спецификация
Описываются **только публичные эндпоинты сайта**. Админские эндпоинты не описываются — для админ-панели достаточно раздела «Админ-панель».

Для каждого публичного эндпоинта:
- Метод, URL
- Request body (JSON)
- Response body (JSON) — успех и ошибки
- HTTP status codes

### Админ-панель
Для каждого экрана: название, перечень полей, доступные действия (создать, просмотреть, редактировать, удалить), права доступа. Действия и права оформляются отдельной таблицей.

### Sequence-диаграмма
PlantUML-диаграмма, описывающая основной бизнес-процесс. Диаграмма логическая: она показывает участников и обмен данными, но не вводит новых архитектурных решений. Конкретные сервисы, хранилища и механизмы кеширования берутся из ADR.

### Нефункциональные требования
Производительность, безопасность, доступность, совместимость — в рамках ограничений из BRD и решений ADR.

### Версии и история
Заполни `Дата`, `Версия`, `Статус`. В основании укажи версии ADR и BRD: `(ADR v1.0, BRD v1.0)`. Если это не первая версия — добавь строку в «Историю изменений» и объясни, что изменилось в ADR или BRD.

6. **Построй матрицу трассировки** BR → FR (таблица: BR-ID → FR-ID).
7. **Сохрани** как `features/<slug>/03-FR.md`.
8. **Выведи пользователю резюме** (до 10 строк): количество FR, публичных API-эндпоинтов, сущностей БД.
9. **Запроси подтверждение**: "FR сформирован. Согласовано? (ок/дальше/approved)"

## Чек-лист качества

- [ ] Каждое бизнес-требование из BRD трассировано в FR (есть таблица трассировки)
- [ ] Все архитектурные решения из ADR нашли отражение в FR (данные, API, админка, NFR)
- [ ] FR не выбирает сервисы, хранилища и механизмы кеширования — это зона ADR
- [ ] API-спецификация описывает только публичную часть сайта
- [ ] У каждого публичного API-эндпоинта есть пример запроса и ответа
- [ ] Для админ-экранов указаны действия и права доступа
- [ ] Параметры БД (поля, типы, nullable) сходятся с описанием API
- [ ] Описание БД следует Database Design Guide (именование: snake_case, типы)
- [ ] API-спецификация следует API Design Guide (RESTful, единые форматы ответов)
- [ ] Sequence-диаграмма описывает как минимум основной сценарий
- [ ] В основании указаны версии ADR и BRD; раздел «История изменений» заполнен

## Чего НЕ делать

- Не переходить к тест-кейсам без подтверждения пользователя
- Не придумывать требования, которых нет в BRD или ADR
- Не описывать админские API-эндпоинты
