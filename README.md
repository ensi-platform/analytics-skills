# AI-агенты по производству аналитических артефактов

Проект автоматизирует генерацию аналитической документации двумя AI-агентами — аналитиком и QA — на основе короткого запроса пользователя.

Методология: **BRD → ADR → FR → QA (применимые документы проверок и Matrix)**.

## Как пользоваться

1. Открой проект в Codex или OpenCode и начни работу с аналитиком. В OpenCode агент **`analyst`** задан по умолчанию для новых сессий в `opencode.jsonc`; в Codex используй инструкцию `.opencode/agents/analyst.md`.
2. Напиши короткое описание требований (1–3 строки), например: «Хочу сделать управление баннерами».
3. Аналитик создаст папку `features/<slug>/` и **BRD** — согласуй его. Затем по очереди согласуй **ADR** и **FR**. После каждого этапа агент ждёт явного подтверждения.
4. После согласования FR аналитик проверит готовность BRD, ADR и FR. Выбери тип QA-документации: **тест-кейсы** или **чек-листы**. Если ты уже указал тип для этой фичи, повторный выбор не потребуется. Если QA-этап не отложен, после выбора основной агент автоматически передаст задачу отдельному QA-субагенту.
5. QA-агент подготовит функциональный документ выбранного типа, документы Integration и API при наличии применимых проверок и **Matrix** по фактическим проверкам. Неприменимость категории объясняется в Matrix по основаниям; временная блокировка и нехватка данных не означают неприменимости. Все созданные документы готовятся в одном этапе и представляются вместе. Согласуй комплект с перечислением версий либо отдельные документы; этап завершён после согласования всех созданных документов. Если основания не готовы, подготовка остановится с указанием причины.

Если QA обнаружит вопросы к требованиям, основной агент вынесет необходимые решения на твоё согласование и передаст корректировку аналитику. После изменений и повторного согласования затронутых оснований задача вернётся QA с актуальными версиями.

Правила передачи находятся в разделе 8 `AGENTS.md`, обязанности исполнителей — в `.opencode/agents/analyst.md` и `.opencode/agents/qa.md`. Отдельный агент-координатор не требуется: основной агент организует передачу, а содержание документов остаётся ответственностью соответствующей роли.

В OpenCode аналитик имеет `mode: primary`, QA — `mode: all`, чтобы его можно было вызвать как субагента или выбрать самостоятельно. В Codex основной агент запускает отдельного субагента средствами Codex и явно поручает ему прочитать инструкцию QA; настройка `mode` в `.opencode` сама по себе этот запуск не выполняет. Настройка ролей OpenCode описана в [документации](https://opencode.ai/docs/agents/).

Факт передачи подтверждается записью запуска отдельного субагента с его идентификатором в журнале действий. Если среда не позволяет вызвать субагента, основной агент сообщит, что передача не состоялась, и предложит ручной запуск QA. В этом случае выбери QA и передай, например: «Подготовь тест-кейсы для `features/banner-management/` по согласованным BRD, ADR и FR, тип — тест-кейсы». Основания передаются через файлы, история другого чата не требуется.

Результат — 3 согласованных аналитических документа и согласованный QA-комплект, состав которого определяется применимостью проверок; функциональный документ и Matrix обязательны. Архитектурные схемы хранятся в `analytical documents/diagrams/`. Все рабочие версии документов сразу сохраняются в соответствующих папках, независимо от статуса согласования.

## Изменения и версии

Согласованный документ не переписывается молча: любая правка — это новая версия. `1.1` — уточнения без изменения смысла, `2.0` — изменение требований или решений. При изменении вышестоящего документа зависимые помечаются статусом «Устарел» и согласуются заново по цепочке BRD → ADR → FR → фактический QA-комплект. Уточнения без изменения смысла (`1.x`) каскад не запускают: в зависимых документах обновляются версии оснований и история. При изменении тест-кейсов или чек-листов QA синхронизирует матрицу покрытия, её ссылки и версии документов с проверками. Что именно менялось — видно в разделе «История изменений» в конце каждого документа.

## Структура проекта

```
AGENTS.md                # Общие правила, согласование, версии и передача между агентами
opencode.jsonc           # Агент analyst по умолчанию и разрешения
PROJECT-MAP.md           # Карта проекта: домены, сервисы, архитектурные принципы
.opencode/
  agents/
    analyst.md           # Агент аналитик: BRD → ADR → FR
    qa.md                # Агент QA: применимые документы по согласованным основаниям
  skills/
    brd-generator/
      SKILL.md           # Скилл генерации BRD
      templates/
        BRD.md           # Шаблон Business Requirements Document
    adr-generator/
      SKILL.md           # Скилл генерации ADR
      templates/
        ADR.md           # Шаблон Architecture Decision Record
    fr-generator/
      SKILL.md           # Скилл генерации FR
      templates/
        FR.md            # Шаблон Functional Requirements Document
    testcases-generator/
      SKILL.md           # Скилл подготовки тест-кейсов и чек-листов
      templates/
        Functional TC.md
        Integration TC.md
        API TC.md
        Functional CL.md
        Integration CL.md
        API CL.md
        Matrix.md
features/
  <feature-slug>/        # Папка конкретной фичи (создаётся агентом)
    analytical documents/
      01-BRD.md
      02-ADR.md
      03-FR.md
      diagrams/
        architecture.c4    # Схема взаимодействия сервисов (LikeC4)
        likec4.config.json # Отдельный LikeC4-проект (name = slug)
    testing documents/
      Functional TC.md или Functional CL.md
      Integration TC.md или Integration CL.md  # при наличии применимых проверок
      API TC.md или API CL.md                  # при наличии применимых проверок
      Matrix.md
README.md                # Этот файл
```

## Формат запроса

Любой текст в свободной форме, содержащий:
- Что нужно сделать
- Кто будет использовать
- Какой ожидается результат

Пример: *"Сделать личный кабинет пользователя с историей заказов и возможностью вернуть товар"*.

## Схемы в ADR

Схема взаимодействия сервисов лежит отдельным файлом `features/<slug>/analytical documents/diagrams/architecture.c4` — в документ она не встраивается, потому что превью Markdown не рендерит LikeC4. В ADR остаются ссылка на файл и расшифровка потоков текстом.

Файл создаётся из каркаса `.opencode/skills/adr-generator/templates/architecture.c4.tpl`: восемь видов элементов с формами (`person`, `browser`, `component`, `cylinder`, `queue`, `bucket`) и цветами. Иконки не используются — смысл несут форма, цвет и автоматическая легенда (`notation`). Стек показывается текстом в `technology`.

Рядом со схемой обязателен `analytical documents/diagrams/likec4.config.json` (`name` = slug фичи). Он делает папку отдельным LikeC4-проектом: иначе LikeC4 собирает все `*.c4` репозитория в один проект, и схемы разных фич конфликтуют — `Duplicate element kind`, `Duplicate view 'index'`.

Открыть схему:
- расширение **LikeC4** в VS Code (`likec4.likec4-vscode`) — превью с hot-reload;
- или `npx likec4@latest start` из папки `features/<slug>/analytical documents/diagrams/`, затем `http://localhost:5173`.

Проверка синтаксиса: `npx likec4@latest validate .` — должно быть `✓ Valid`.
