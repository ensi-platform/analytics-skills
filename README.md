# AI-агенты по производству аналитических артефактов

Проект автоматизирует генерацию аналитической документации двумя AI-агентами — аналитиком и QA — на основе короткого запроса пользователя.

Методология: **BRD → ADR → FR → Test Cases**.

## Как пользоваться

1. Открой проект в OpenCode и выбери агента **`analyst`**. Для новых сессий он задан по умолчанию в `opencode.jsonc`.
2. Напиши короткое описание требований (1–3 строки), например: «Хочу сделать управление баннерами».
3. Аналитик создаст папку `features/<slug>/` и **BRD** — согласуй его. Затем по очереди согласуй **ADR** и **FR**. После каждого этапа агент ждёт явного подтверждения.
4. После согласования FR аналитик зафиксирует статусы и версии документов и сообщит путь папки фичи.
5. Выбери отдельного агента **`qa`**. Можно начать новый чат: передача выполняется через сохранённые документы, история чата аналитика не требуется.
6. Напиши, например: «Подготовь тест-кейсы для `features/banner-management/` по согласованным BRD, ADR и FR».
7. QA проверит готовность всех трёх оснований и создаст **Test Cases** — согласуй их. При недостающих или несогласованных основаниях QA сообщит, что нужно завершить у аналитика.

Если QA обнаружит вопросы к требованиям, передай их `analyst`. После изменений и повторного согласования затронутых оснований верни фичу `qa` для обновления тест-кейсов.

Роли определены в отдельных Markdown-файлах с `mode: primary`: каждый агент выбирается как основной для своего чата. `AGENTS.md` содержит общие правила обоих агентов. Настройка ролей описана в [документации OpenCode](https://opencode.ai/docs/agents/).

Результат — 4 согласованных документа в папке фичи.

## Изменения и версии

Согласованный документ не переписывается молча: любая правка — это новая версия. `1.1` — уточнения без изменения смысла, `2.0` — изменение требований или решений. При изменении вышестоящего документа зависимые помечаются статусом «Устарел» и согласуются заново по цепочке BRD → ADR → FR → Test Cases. Уточнения без изменения смысла (`1.x`) каскад не запускают: в зависимых документах обновляются версии оснований и история. Что именно менялось — видно в разделе «История изменений» в конце каждого документа.

## Структура проекта

```
AGENTS.md                # Общие правила, согласование, версии и передача между агентами
opencode.jsonc           # Агент analyst по умолчанию и разрешения
PROJECT-MAP.md           # Карта проекта: домены, сервисы, архитектурные принципы
.opencode/
  agents/
    analyst.md           # Агент аналитик: BRD → ADR → FR
    qa.md                # Агент QA: Test Cases по согласованным основаниям
  skills/
    brd-generator/
      SKILL.md           # Скилл генерации BRD
      templates/
        BRD.md           # Шаблон Business Requirements Document
    adr-generator/
      SKILL.md           # Скилл генерации ADR
      templates/
        ADR.md           # Шаблон Architecture Decision Record
    fr-generator/
      SKILL.md           # Скилл генерации FR
      templates/
        FR.md            # Шаблон Functional Requirements Document
    testcases-generator/
      SKILL.md           # Скилл генерации тест-кейсов
      templates/
        TEST-CASES.md    # Шаблон тест-кейсов
features/
  <feature-slug>/        # Папка конкретной фичи (создаётся агентом)
    01-BRD.md
    02-ADR.md
    03-FR.md
    04-TEST-CASES.md
    diagrams/
      architecture.c4    # Схема взаимодействия сервисов (LikeC4)
      likec4.config.json # Отдельный LikeC4-проект (name = slug)
README.md                # Этот файл
```

## Формат запроса

Любой текст в свободной форме, содержащий:
- Что нужно сделать
- Кто будет использовать
- Какой ожидается результат

Пример: *"Сделать личный кабинет пользователя с историей заказов и возможностью вернуть товар"*.

## Схемы в ADR

Схема взаимодействия сервисов лежит отдельным файлом `features/<slug>/diagrams/architecture.c4` — в документ она не встраивается, потому что превью Markdown не рендерит LikeC4. В ADR остаются ссылка на файл и расшифровка потоков текстом.

Файл создаётся из каркаса `.opencode/skills/adr-generator/templates/architecture.c4.tpl`: восемь видов элементов с формами (`person`, `browser`, `component`, `cylinder`, `queue`, `bucket`) и цветами. Иконки не используются — смысл несут форма, цвет и автоматическая легенда (`notation`). Стек показывается текстом в `technology`.

Рядом со схемой обязателен `diagrams/likec4.config.json` (`name` = slug фичи). Он делает папку отдельным LikeC4-проектом: иначе LikeC4 собирает все `*.c4` репозитория в один проект, и схемы разных фич конфликтуют — `Duplicate element kind`, `Duplicate view 'index'`.

Открыть схему:
- расширение **LikeC4** в VS Code (`likec4.likec4-vscode`) — превью с hot-reload;
- или `npx likec4@latest start` из папки фичи, затем `http://localhost:5173`.

Проверка синтаксиса: `npx likec4@latest validate .` — должно быть `✓ Valid`.
