# AI-агенты по производству аналитических артефактов

Проект автоматизирует генерацию аналитической документации двумя AI-агентами — аналитиком и QA — на основе короткого запроса пользователя.

Методология: **BRD → ADR → FR → QA (применимые документы проверок и Matrix)**.

## Как пользоваться

1. Открой проект в любом агенте, который читает `AGENTS.md` (OpenCode, Codex, Cursor, Claude Code и др.), и начни с роли аналитика `roles/analyst.md`. В OpenCode агент **`analyst`** уже задан по умолчанию в `opencode.jsonc`.
2. Напиши короткое описание требований (1–3 строки), например: «Хочу сделать управление баннерами».
3. Аналитик создаст папку `features/<slug>/` и **BRD** — согласуй его. Затем по очереди согласуй **ADR** и **FR**. После каждого этапа агент ждёт явного подтверждения.
4. После согласования FR аналитик проверит готовность BRD, ADR и FR и наличие PASS или PASS WITH REMARKS в `validation.md`. Выбери тип QA-документации: **тест-кейсы** или **чек-листы**. Если ты уже указал тип для этой фичи, повторный выбор не потребуется. Если QA-этап не отложен, после выбора основной агент автоматически передаст задачу отдельному исполнителю с ролью QA, если среда поддерживает субагентов; иначе предложит запустить QA отдельной сессией.
5. QA-агент подготовит функциональный документ выбранного типа, документы Integration и API при наличии применимых проверок и **Matrix** по фактическим проверкам. Неприменимость категории объясняется в Matrix по основаниям; временная блокировка и нехватка данных не означают неприменимости. Все созданные документы готовятся в одном этапе и представляются вместе. Согласуй комплект с перечислением версий либо отдельные документы; этап завершён после согласования всех созданных документов. Если основания не готовы, подготовка остановится с указанием причины.

Если QA обнаружит вопросы к требованиям, основной агент вынесет необходимые решения на твоё согласование и передаст корректировку аналитику. После изменений и повторного согласования затронутых оснований задача вернётся QA с актуальными версиями.

## Валидация документов

Для новых фич перед показом каждого документа заполняется `features/<slug>/validation/validation.md` по чек-листу `validation/README.md`. Без PASS или PASS WITH REMARKS документ не переводится в «На согласовании». При PASS или PASS WITH REMARKS документ получает статус «На согласовании»; при PASS WITH REMARKS пользователь дополнительно видит существенные замечания и решает, принять их или отправить документ на исправление. Проверку выполняют автор и основной агент; отдельный агент-валидатор и скрипты в v1 не используются. Фичи до внедрения процесса перечислены как legacy в `validation/README.md`: для них валидация выполняется по отдельному решению. После согласования всех документов выполняется финальная проверка комплекта.

Правила передачи находятся в разделе 8 `AGENTS.md`, обязанности исполнителей — в `roles/analyst.md` и `roles/qa.md`. Отдельный агент-координатор не требуется: основной агент организует передачу, а содержание документов остаётся ответственностью соответствующей роли.

Роли описаны обычными Markdown-файлами в `roles/`, поэтому не зависят от инструмента: агент читает `AGENTS.md` и файл своей роли. Автоматический запуск второго исполнителя зависит от среды: в OpenCode это субагент `qa` (QA имеет `mode: all`), в остальных — собственный механизм субагентов или отдельная сессия. Подробности — в разделе «Другие агенты».

Факт передачи подтверждается запуском отдельного исполнителя с его идентификатором в журнале действий. Если среда не позволяет запустить отдельного исполнителя, основной агент сообщит, что передача не состоялась, и предложит ручной запуск QA. В этом случае открой новую сессию, укажи роль `roles/qa.md` и передай, например: «Подготовь тест-кейсы для `features/banner-management/` по согласованным BRD, ADR и FR, тип — тест-кейсы». Основания передаются через файлы, история другого чата не требуется.

Результат — 3 согласованных аналитических документа, `validation.md` и согласованный QA-комплект, состав которого определяется применимостью проверок; функциональный документ и Matrix обязательны. Архитектурные схемы хранятся в `analytical documents/diagrams/`. Все рабочие версии документов сразу сохраняются в соответствующих папках, независимо от статуса согласования.

## Другие агенты

Проект не привязан к конкретному инструменту: правила лежат в `AGENTS.md`, роли — в `roles/`, скиллы — в `.agents/skills/` (открытый стандарт Agent Skills).

**Универсальный запуск:** открой проект и напиши агенту «Прочитай `AGENTS.md` и `roles/analyst.md` и работай по ним». Дальше — как в разделе «Как пользоваться». Когда дойдёт до QA, открой вторую сессию с той же фразой, но про `roles/qa.md`.

| Инструмент | Корневой файл | Скиллы | Запуск QA | Статус |
|---|---|---|---|---|
| OpenCode | `AGENTS.md` | `.agents/skills/` | субагент `qa` | проверено |
| Claude Code | `CLAUDE.md` (импортирует `AGENTS.md`) | `.claude/skills/` — симлинк на `.agents/skills/` | отдельная сессия | требует проверки |
| Codex | `AGENTS.md` | `.agents/skills/` | отдельная сессия | требует проверки |
| Cursor, Copilot, Gemini | `AGENTS.md` | `.agents/skills/` | отдельная сессия | требует проверки |
| Hermes | `AGENTS.md` как workspace instructions | стандарт agentskills.io | отдельная сессия | требует проверки |
| DeepSeek Harness | требует уточнения | требует уточнения | отдельная сессия | требует уточнения |

«Требует проверки» означает, что поддержка ожидается по документации инструмента, но полный прогон в этом проекте не выполнялся; результат фиксируй в таблице.

Для Claude Code один раз выполни:

```bash
mkdir -p .claude
[ -e .claude/skills ] || [ -L .claude/skills ] || ln -s ../.agents/skills .claude/skills
```

Первая команда создаст каталог `.claude`, если его ещё нет. Вторая создаст симлинк, только если `.claude/skills` ещё не существует, и не тронет уже созданный (в том числе битый) симлинк. Симлинк локальный и исключён из коммитов через `.gitignore`. На Windows для создания симлинка нужен режим разработчика или права администратора; в Git Bash `ln -s` без спецнастроек может создать копию вместо ссылки.

Автоматический запуск субагента есть не в каждой среде. Если его нет, передача QA выполняется отдельной сессией — это штатный режим, а не сбой.

## Изменения и версии

Согласованный документ не переписывается молча: любая правка — это новая версия. `1.1` — уточнения без изменения смысла, `2.0` — изменение требований или решений. При изменении вышестоящего документа зависимые помечаются статусом «Устарел» и согласуются заново по цепочке BRD → ADR → FR → фактический QA-комплект. Уточнения без изменения смысла (`1.x`) каскад не запускают: в зависимых документах обновляются версии оснований и история. При изменении тест-кейсов или чек-листов QA синхронизирует матрицу покрытия, её ссылки и версии документов с проверками. Перед показом изменённого документа валидация выполняется заново, а согласованные версии фиксируются в `validation.md`. Что именно менялось — видно в разделе «История изменений» в конце каждого документа.

## Формат запроса

Любой текст в свободной форме, содержащий:
- Что нужно сделать
- Кто будет использовать
- Какой ожидается результат

Пример: *"Сделать личный кабинет пользователя с историей заказов и возможностью вернуть товар"*.

## Схемы в ADR

Схема взаимодействия сервисов лежит отдельным файлом `features/<slug>/analytical documents/diagrams/architecture.c4` — в документ она не встраивается, потому что превью Markdown не рендерит LikeC4. В ADR остаются ссылка на файл и расшифровка потоков текстом.

Файл создаётся из каркаса `.agents/skills/adr-generator/templates/architecture.c4.tpl`: восемь видов элементов с формами (`person`, `browser`, `component`, `cylinder`, `queue`, `bucket`) и цветами. Иконки не используются — смысл несут форма, цвет и автоматическая легенда (`notation`). Стек показывается текстом в `technology`.

Рядом со схемой обязателен `analytical documents/diagrams/likec4.config.json` (`name` = slug фичи). Он делает папку отдельным LikeC4-проектом: иначе LikeC4 собирает все `*.c4` репозитория в один проект, и схемы разных фич конфликтуют — `Duplicate element kind`, `Duplicate view 'index'`.

Открыть схему:
- расширение **LikeC4** в VS Code (`likec4.likec4-vscode`) — превью с hot-reload;
- или `npx likec4@latest start` из папки `features/<slug>/analytical documents/diagrams/`, затем `http://localhost:5173`.

Проверка синтаксиса: `npx likec4@latest validate .` — должно быть `✓ Valid`.
