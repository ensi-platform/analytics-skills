# Скилл: Генерация FR

## Когда применять

ADR согласован пользователем (получено подтверждение "согласовано", "ок", "дальше", "approved", "хорошо"). FR создаётся после ADR: архитектурные решения уже зафиксированы, остаётся описать функциональность.

## Входные данные

- `features/<slug>/analytical documents/01-BRD.md` — согласованный Business Requirements Document
- `features/<slug>/analytical documents/02-ADR.md` — согласованный Architecture Decision Record
- `PROJECT-MAP.md` — карта проекта: домены, сервисы, архитектурные принципы
- `templates/FR.md` — шаблон функциональных требований (путь относительно каталога скилла)

## Действия

1. **Прочитай** `01-BRD.md` и `02-ADR.md` из `features/<slug>/analytical documents/`.
2. **Прочитай** `PROJECT-MAP.md` в корне проекта.
3. **Прочитай шаблон** `templates/FR.md` (путь относительно каталога скилла).
4. **Прочитай правила** `AGENTS.md` (в корне проекта).
5. **Заполни шаблон**, покрывая все разделы:

### Функциональные требования
Формат User Story от трёх лиц:
- **Пользователь сайта** — "Как пользователь, я хочу..."
- **Администратор в панели управления** — "Как администратор, я хочу..."
- **Backend-сервис** — "Как система, я должна..."

Каждая User Story содержит: ID (FR-01...), роль, действие, обоснование, критерий приёмки.

### Модель данных
Таблицы с колонками:

| Наименование | Тип | Nullable | Описание |
|---|---|---|---|
| `id` | int | Нет | Первичный ключ |

Связи между сущностями описать текстом.

### API-спецификация
Описываются **только публичные эндпоинты сайта**. Админские эндпоинты не описываются — для админ-панели достаточно раздела «Админ-панель».

Для каждого публичного эндпоинта:
- Метод, URL
- Request body (JSON)
- Response body (JSON) — успех и ошибки
- HTTP status codes

### Админ-панель
Для каждого экрана: название, перечень полей, доступные действия (создать, просмотреть, редактировать, удалить), права доступа. Действия и права оформляются отдельной таблицей.

### Sequence-диаграмма
PlantUML-диаграмма, описывающая основной бизнес-процесс. Диаграмма логическая: она показывает участников и обмен данными, но не вводит новых архитектурных решений. Конкретные сервисы, хранилища и механизмы кеширования берутся из ADR.

### Нефункциональные требования
Производительность, безопасность, доступность, совместимость — в рамках ограничений из BRD и решений ADR.

### Версии и история
Заполни `Дата`, `Версия`, `Статус`. В основании укажи версии ADR и BRD: `(ADR v1.0, BRD v1.0)`. Если это не первая версия — добавь строку в «Историю изменений» и объясни, что изменилось в ADR или BRD.

6. **Построй матрицу трассировки** BR → FR (таблица: BR-ID → FR-ID).
7. **Построй матрицу трассировки** ADR → FR (таблица: ADR-ID → FR-ID/раздел).
8. **Сохрани** как `features/<slug>/analytical documents/03-FR.md`.
9. **Определи режим валидации по `validation/README.md`.** Если валидация включена, заполни или обнови `features/<slug>/validation/validation.md`; после актуального PASS или PASS WITH REMARKS установи статус «На согласовании» и покажи FR. При PASS WITH REMARKS перечисли существенные замечания и зафиксируй решение пользователя; при FAIL исправь документ и повтори проверку. Если для legacy-фичи валидация не включена и отчёт отсутствует, переведи FR в «На согласовании» после самопроверки и не создавай отчёт автоматически.
10. **Выведи пользователю резюме** (до 10 строк): количество FR, публичных API-эндпоинтов, сущностей БД, вердикт валидации и существенные замечания, если они есть.
11. **Запроси подтверждение**: "FR сформирован. Согласовано? (ок/дальше/approved)"

## Валидация

Определи режим валидации по `validation/README.md`. Если валидация включена, перед показом FR заполни или обнови `features/<slug>/validation/validation.md`. Проверь готовность BRD и ADR, трассировку BR → FR и ADR → FR, историю и отсутствие заглушек. Показывай FR только при PASS или PASS WITH REMARKS; при FAIL исправь документ и повтори проверку. При PASS или PASS WITH REMARKS установи статус «На согласовании». При PASS WITH REMARKS перечисли существенные замечания и зафиксируй решение пользователя по ним. Если пользователь требует исправлений, верни FR в «Черновик», оформи новую версию и повтори валидацию. Если для legacy-фичи валидация не включена и отчёт отсутствует, переведи FR в «На согласовании» после самопроверки и не создавай отчёт автоматически. Если legacy-отчёт уже существует, поддерживай его актуальным после изменений без отдельного запроса пользователя. В резюме укажи вердикт валидации, если он применим, и существенные замечания, если они есть.

## Чек-лист качества

- [ ] Каждое бизнес-требование из BRD трассировано в FR (есть таблица трассировки)
- [ ] Все архитектурные решения из ADR нашли отражение в FR (данные, API, админка, NFR) и в таблице ADR → FR
- [ ] FR не выбирает сервисы, хранилища и механизмы кеширования — это зона ADR
- [ ] API-спецификация описывает только публичную часть сайта
- [ ] У каждого публичного API-эндпоинта есть пример запроса и ответа
- [ ] Для админ-экранов указаны действия и права доступа
- [ ] Параметры БД (поля, типы, nullable) сходятся с описанием API
- [ ] Описание БД следует Database Design Guide (именование: snake_case, типы)
- [ ] API-спецификация следует API Design Guide (RESTful, единые форматы ответов)
- [ ] Sequence-диаграмма описывает как минимум основной сценарий
- [ ] В основании указаны версии ADR и BRD; раздел «История изменений» заполнен
- [ ] Валидация по `validation/README.md` пройдена, `validation.md` заполнен

## Чего НЕ делать

- Не переходить к QA без согласования FR и выбора пользователем типа QA-документации по разделу 8 `AGENTS.md`.
- Не придумывать требования, которых нет в BRD или ADR
- Не описывать админские API-эндпоинты
