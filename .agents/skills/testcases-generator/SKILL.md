# Подготовка QA-документов

Общие правила — в [AGENTS.md](../../../AGENTS.md), приём задачи, проектирование проверок и представление комплекта — в [инструкции QA](../../../roles/qa.md).

## Вход и результат

- Основания: `01-BRD.md`, `02-ADR.md` и `03-FR.md` из `features/<slug>/analytical documents/`.
- При переработке прочитай весь текущий QA-комплект; при разделении старого формата — исходный `04-TEST-CASES.md`.
- Получи явный выбор пользователя: тест-кейсы или чек-листы. Если выбор отсутствует, не начинай подготовку и запроси его по разделу 8 `AGENTS.md`.
- Сохраняй функциональный документ, применимые документы Integration и API и Matrix в `features/<slug>/testing documents/` по соответствующим шаблонам:

| Категория | Тест-кейсы | Чек-листы |
|---|---|---|
| Функциональные | [Functional TC](templates/Functional%20TC.md) | [Functional CL](templates/Functional%20CL.md) |
| Интеграционные | [Integration TC](templates/Integration%20TC.md) | [Integration CL](templates/Integration%20CL.md) |
| API | [API TC](templates/API%20TC.md) | [API CL](templates/API%20CL.md) |
| Матрица | [Matrix](templates/Matrix.md) | [Matrix](templates/Matrix.md) |

## Валидация

Определи режим валидации по `validation/README.md`. Если валидация включена, перед показом комплекта создай или обнови `features/<slug>/validation/validation.md`. Проверь полноту Matrix, существование ID, сходимость сводок, единство типа и обоснованность неприменимости категорий. Показывай комплект только при PASS или PASS WITH REMARKS; при FAIL исправь документы и повтори проверку. При PASS или PASS WITH REMARKS установи статус «На согласовании» для всех созданных документов. При PASS WITH REMARKS перечисли существенные замечания и зафиксируй решение пользователя по ним. Если пользователь требует исправлений, верни затронутые документы в «Черновик», оформи новые версии и повтори валидацию. Если для legacy-фичи валидация не включена и отчёт отсутствует, переведи комплект в «На согласовании» после проверки оснований и не создавай отчёт автоматически. Если legacy-отчёт уже существует, поддерживай его актуальным после изменений без отдельного запроса пользователя. В резюме укажи вердикт валидации, если он применим, и существенные замечания, если они есть.

## Подготовка

1. Подготовь функциональный документ и документы категорий Integration и API, в которых есть применимые проверки. Если основание подтверждает неприменимость категории, новый файл не создавай, а обоснование со ссылкой на основание укажи в Matrix; отсутствие данных, стенда и временная блокировка не доказывают неприменимости. Применимые проверки с пробелами сохраняй заблокированными. Если применимость невозможно определить, зафиксируй вопрос, запроси уточнение и не объявляй комплект полным. Существующие файлы не удаляй только из-за этого правила.
2. После подготовки документов проверок собери Matrix по их фактическим проверкам без ожидания согласования. Для каждого FR и решения ADR в столбце «Покрывающие проверки» перечисли через запятую только полные ID связанных тест-кейсов или чек-листов выбранного типа, без названий категорий и пояснений. Частичное покрытие, конкретные пробелы и блокировки укажи в соседнем столбце. Ссылайся на фактические файлы и версии выбранного комплекта, отсутствующие неприменимые категории объясняй без несуществующих ссылок. Учитывай каждый тест-кейс или чек-лист один раз, не подсчитывай отдельные пункты как отдельные чек-листы. Общие ограничения опиши один раз перед таблицами.
3. Сверь комплект: ID проверок и вопросов, блокировки, локальные и общие количества, приоритеты, ссылки и версии документов должны совпадать. Условия и данные должны быть доступны из каждого документа с проверками.

### Общие условия и тестовые данные

Описывай подготовку кратко и простыми словами: оставляй только данные, роли, связи, настройки и действия по восстановлению, необходимые для проверок конкретного документа. Используй понятные названия; если без условных обозначений не обойтись, расшифруй их в небольшой таблице рядом с данными. Не повторяй условия и оговорки без необходимости; детали отдельной проверки оставляй рядом с ней. Каждый документ с проверками должен содержать достаточно сведений для самостоятельного выполнения.

### Оформление чек-листов

- Поля шапки отделяй пустыми строками, чтобы они отображались отдельными строками в Markdown. Общие условия и данные представляй кратким списком или таблицей без потери ограничений и подготовки.
- В описании интеграции поля «Системы», «Протокол», «Описание», «Документация» и «Статус проверки» отделяй пустыми строками, чтобы каждое отображалось отдельно в Markdown; правило относится к обоим типам QA-документов.
- Каждый чек-лист размещай в отдельном Markdown-блоке: ID и название, приоритет, ссылки на связанные FR и ADR, предусловие либо блокер с ID вопроса, затем список проверок. Сохраняй формат маркеров соответствующего шаблона; не отмечай выполнение без реального результата.
- Формулируй каждый пункт как отдельный конкретный наблюдаемый результат. Разделяй разные граничные случаи, условия и результаты, если это улучшает проверяемость; не добавляй новые требования. Если данных нет, фиксируй вопрос и блокируй затронутые проверки по правилам QA.

Изменения и перенос из объединённого документа выполняй по разделу «Изменения и разделение существующего документа» инструкции QA.
