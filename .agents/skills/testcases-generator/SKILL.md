# Подготовка QA-документов

Общие правила — в [AGENTS.md](../../../AGENTS.md), приём задачи, проектирование проверок и представление комплекта — в [инструкции QA](../../../roles/qa.md).

## Вход и результат

- Основания: `01-BRD.md`, `02-ADR.md` и `03-FR.md` из `features/<slug>/analytical documents/`.
- При переработке прочитай весь текущий QA-комплект; при разделении старого формата — исходный `04-TEST-CASES.md`.
- Получи явный выбор пользователя: тест-кейсы или чек-листы. Если выбор отсутствует, не начинай подготовку и запроси его по разделу 8 `AGENTS.md`.
- Сохраняй функциональный документ, применимые документы Integration и API и Matrix в `features/<slug>/testing documents/` по соответствующим шаблонам:

| Категория | Тест-кейсы | Чек-листы |
|---|---|---|
| Функциональные | [Functional TC](templates/Functional%20TC.md) | [Functional CL](templates/Functional%20CL.md) |
| Интеграционные | [Integration TC](templates/Integration%20TC.md) | [Integration CL](templates/Integration%20CL.md) |
| API | [API TC](templates/API%20TC.md) | [API CL](templates/API%20CL.md) |
| Матрица | [Matrix](templates/Matrix.md) | [Matrix](templates/Matrix.md) |

## Валидация

Определи режим валидации по `validation/README.md`. Если валидация включена, сохрани комплект как «Черновик», проведи самопроверку и передай документы основному агенту. Проверь полноту Matrix, существование ID, сходимость сводок, единство типа и обоснованность неприменимости категорий. Основной агент проверяет комплект по файлам, создаёт или обновляет `features/<slug>/validation/validation.md` и передаёт вердикт QA. При FAIL исправь документы и передай их на повторную проверку; при актуальном PASS или PASS WITH REMARKS установи статус «На согласовании». Комплект показывает основной агент; при PASS WITH REMARKS он перечисляет существенные замечания и фиксирует решение пользователя в отчёте. Если пользователь требует исправлений, верни затронутые документы в «Черновик», оформи новые версии и повтори процесс проверки. После согласования основной агент обновляет отчёт. Если QA работает без основного агента, он выполняет обе проверки, ведёт отчёт и показывает комплект самостоятельно. Если для legacy-фичи валидация не включена и отчёт отсутствует, переведи комплект в «На согласовании» после проверки оснований и самопроверки, не создавая отчёт. Если legacy-отчёт уже существует, основной агент поддерживает его актуальным после изменений без отдельного запроса пользователя. В резюме укажи применимый вердикт и существенные замечания.

## Подготовка

1. Подготовь функциональный документ и документы категорий Integration и API, в которых есть применимые проверки. Если основание подтверждает неприменимость категории, новый файл не создавай, а обоснование со ссылкой на основание укажи в Matrix; отсутствие данных, стенда и временная блокировка не доказывают неприменимости. Применимые проверки с пробелами сохраняй заблокированными. Если применимость невозможно определить, зафиксируй вопрос, запроси уточнение и не объявляй комплект полным. Существующие файлы не удаляй только из-за этого правила.
2. После подготовки документов проверок собери Matrix по их фактическим проверкам без ожидания согласования. Для каждого FR и решения ADR в столбце «Покрывающие проверки» перечисли через запятую только полные ID связанных тест-кейсов или чек-листов выбранного типа, без названий категорий и пояснений. Частичное покрытие, конкретные пробелы и блокировки укажи в соседнем столбце. Ссылайся на фактические файлы и версии выбранного комплекта, отсутствующие неприменимые категории объясняй без несуществующих ссылок. Учитывай каждый ID один раз: в функциональном, интеграционном и API-чек-листах ID соответствует строке таблицы. Общие ограничения опиши один раз перед таблицами.
3. Сверь комплект: ID проверок и вопросов, блокировки, локальные и общие количества, критичность, ссылки и версии документов должны совпадать.

### Условия проверок

Не добавляй отдельный раздел «Общие условия и тестовые данные». Условия, ограничения и сведения, необходимые для конкретной проверки, указывай рядом с ней по шаблону. Не повторяй их без необходимости.

Не создавай отдельный столбец тестовых или входных данных. В предварительных условиях, шагах, пунктах проверки и ожидаемых результатах описывай необходимые роли, состояния и действия понятными словами, без произвольных имён, сокращений и привязки к конкретным тестовым записям. Например, вместо «покупатель B вошёл на сайт» пиши «авторизованный пользователь вошёл на сайт». Если сценарий требует нескольких участников, различай их по роли или отношению к объекту, например «владелец товара» и «другой пользователь». Сохраняй заданные в основаниях значения, границы, методы и параметры API, коды ответа и другие точные условия, когда они существенны для проверки; неизвестное не придумывай.

В столбце «Предварительные условия» / «Предусловия» тест-кейса перечисляй только конкретные действия подготовки и состояния, необходимые до начала проверки данного сценария. Каждое отдельное условие размещай с новой строки внутри ячейки Markdown-таблицы через `<br>`. Не повторяй в каждой строке общие формулировки без конкретного действия или состояния, например «изолированные тестовые данные», и не добавляй подпись «Условие сценария». Если изоляция существенна для сценария, вместо общей фразы опиши конкретное необходимое состояние или действие. При отсутствии необходимых предварительных условий укажи «Не требуются»; неизвестные условия не выдумывай, зафиксируй вопрос и блокировку.

### Оформление чек-листов

- Поля шапки отделяй пустыми строками, чтобы они отображались отдельными строками в Markdown.
- В описании интеграции отделяй поля пустыми строками, чтобы каждое отображалось отдельно в Markdown; правило относится к обоим типам QA-документов.
- Проверки размещай строками по шаблонам. Для интеграций указывай взаимодействие систем, для API — метод и endpoint. Указывай связи с FR и ADR, необходимые предусловия и блокеры с ID вопросов рядом с проверкой. Не отмечай выполнение без реального результата.
- В столбце «Название» кратко указывай, что проверяется. В столбце «Проверка» перечисляй необходимые действия и существенные условия; каждое действие размещай с новой строки через `<br>`. Объединяй подготовку с действием, когда это возможно: «Открыть карточку продавца с номером». Не повторяй название или ожидаемый результат, не добавляй общие фразы и подписи «Проверить:», «Условия:», «Дополнительные условия:». Сохраняй различия сценариев и существенные значения.
- Каждая строка проверяет отдельный результат; укажи его в столбце «Ожидание». Разделяй граничные случаи и условия, когда это улучшает проверяемость; не добавляй новые требования.

Изменения и перенос из объединённого документа выполняй по разделу «Изменения и разделение существующего документа» инструкции QA.
