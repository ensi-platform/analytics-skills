# Скилл: Генерация BRD

## Когда применять

На вход пришёл запрос вида "хочу X", "нужно Y", "сделать Z". Папки фичи ещё не существует.

## Входные данные

- 1–3 строки требований от пользователя
- `PROJECT-MAP.md` — карта проекта: домены, сервисы, архитектурные принципы
- Контекст проекта (текущая структура, если есть)

## Действия

1. **Прочитай** `PROJECT-MAP.md` — чтобы не изобретать сущности и домены, которые уже существуют в проекте.
2. **Определи slug фичи** — латиница, kebab-case, без дат.
3. **Создай директорию** `features/<slug>/analytical documents/`.
4. **Прочитай шаблон** `templates/BRD.md` (путь относительно каталога скилла).
5. **Прочитай правила** `AGENTS.md` (в корне проекта).
6. **Заполни шаблон**:
   - Контекст и цель — на основе запроса пользователя
   - Проблема — какую проблему решает фича
   - Бизнес-требования — в формате BR-01, BR-02, ...
   - User Story — таблица (пользователь, действие, ожидаемый результат)
   - Ограничения — нефункциональные рамки: производительность, доступность, форматы файлов, сроки (если известны). Это вход для ADR: без ограничений архитектурные решения принимаются вслепую
   - Открытые вопросы — если данных недостаточно
   - Шапку документа — `Дата`, `Версия: 1.0`, `Статус: Черновик`
7. **Сохрани** результат как `features/<slug>/analytical documents/01-BRD.md`.
8. **Определи режим валидации по `validation/README.md`.** Если валидация включена, выполни самопроверку, установи статус «Готово к валидации» и сообщи пользователю запустить `/validate <путь к BRD>`; отчёт `features/<slug>/validation/validation.md` ведёт валидатор, сам его не заполняй. После вердикта PASS или PASS WITH REMARKS установи «На согласовании» и покажи BRD; при PASS WITH REMARKS перечисли существенные замечания и зафиксируй решение пользователя; при FAIL исправь документ, оформи новую версию и снова переведи в «Готово к валидации». Если валидация не включена (legacy без отчёта), переведи BRD в «На согласовании» после самопроверки и не создавай отчёт автоматически.
9. **Выведи пользователю краткое резюме** (до 10 строк):
   - Название фичи
   - Slug
   - Количество бизнес-требований и их перечень
   - Ключевые ограничения
   - Ключевые риски
   - Вердикт валидации
   - Существенные замечания, если они есть
   - Ссылку на файл
10. **Запроси подтверждение**: "BRD сформирован. Согласовано? (ок/дальше/approved)"

## Валидация

Определи режим валидации по `validation/README.md`. Валидация включена, если фича новая, у legacy-фичи уже есть `validation.md` или пользователь запросил ретровалидацию. Если валидация включена, отчёт `features/<slug>/validation/validation.md` ведёт валидатор: выполни самопроверку, установи статус «Готово к валидации» и сообщи пользователю запустить `/validate <путь к BRD>`; сам отчёт не заполняй. Показывай BRD только при вердикте PASS или PASS WITH REMARKS; при FAIL исправь документ, оформи новую версию и снова переведи в «Готово к валидации». При PASS или PASS WITH REMARKS установи статус «На согласовании». При PASS WITH REMARKS перечисли существенные замечания и зафиксируй решение пользователя по ним. Если пользователь требует исправлений, верни BRD в «Черновик», оформи новую версию и повтори валидацию. Если валидация не включена (legacy без отчёта), переведи BRD в «На согласовании» после самопроверки и не создавай отчёт автоматически. В резюме укажи вердикт валидации, если он применим, и существенные замечания, если они есть.

## Чек-лист качества

- [ ] Цель сформулирована измеримо (есть числовые или качественные критерии)
- [ ] Определены критерии успеха (KPI / success metrics)
- [ ] Описаны риски
- [ ] Нет системных деталей (API и БД — это FR, архитектура — это ADR)
- [ ] Зафиксированы известные нефункциональные ограничения (производительность, доступность, форматы файлов)
- [ ] Ограничений достаточно, чтобы на них можно было опереться в ADR
- [ ] Раздел «История изменений» заполнен
- [ ] Каждое требование имеет уникальный ID (BR-01, BR-02, ...)
- [ ] Для фичи с включённой валидацией валидатор вернул PASS или PASS WITH REMARKS; отчёт `validation.md` заполнен валидатором

## Чего НЕ делать

- Не описывать API, БД, схемы данных, диаграммы последовательности
- Не использовать техническую терминологию реализации
- Не придумывать требования, которых нет во входных данных
- Не переходить к ADR без подтверждения пользователя
